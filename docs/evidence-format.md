# Evidence Format and Trust Model

Evidra stores claims and MCP-boundary observations as a signed, hash-linked event
stream. This page defines what is written and how far its trust guarantees reach.

## Recorder directory

Passing `--evidence-dir <root>` makes each endpoint process create one child
directory named like `recorder-YYYYMMDD-HHMMSS-<random>`:

```text
<root>/
└─ recorder-20260914-120000-a1b2c3d4/
   ├─ events.jsonl
   ├─ meta.json
   ├─ signing.key
   └─ digest.key
```

The recorder directory is created with mode `0700`; event, metadata, and key
files are created with mode `0600`. An already-created root retains the
permissions chosen by its owner.

`meta.json` contains:

- `schema_version`, currently `evidra.evidence.v2`;
- `created_at` and `recorder_instance_id`;
- `upstream_id`, optional `server_name`, and the upstream command string;
- the base64 Ed25519 `public_key`;
- `digest_key_id`, identifying the local fingerprint comparison domain;
- `enforce_mode`.

The upstream command is readable metadata. Do not place secrets directly on its
command line if the recorder directory will be shared.

## Event envelope

Each line of `events.jsonl` is one JSON object with these envelope fields:

| Field | Meaning |
|---|---|
| `schema_version` | Evidence schema identifier. |
| `seq` | Monotonic sequence within this recorder file. |
| `event_id` | ULID-based event identifier. |
| `event_type` | Payload discriminator. |
| `recorded_at` | Recorder timestamp in UTC. |
| `recorder_instance_id` | Recorder identity copied from metadata. |
| `session_id` | MCP session identifier when applicable. |
| `operation_id` | Open operation identifier when applicable. |
| `upstream_id`, `server_name` | Wrapped-upstream labels. |
| `actor` | Actor reference: `id` may be empty when not configured; `version` is optional. There is no domain verification. |
| `provenance` | Ownership of the statement in this event. |
| `payload` | Event-specific JSON. |
| `previous_hash` | Hex hash of the preceding event, empty at genesis. |
| `hash` | SHA-256 of the canonical unsigned envelope. |
| `signature` | Base64 Ed25519 signature of the hash bytes. |

Readable objectives, expected outcomes, report summaries, and other agent text
are deliberately stored in operation payloads. They may contain sensitive data;
do not put secrets in declarations or reports.

## Event types

The schema has these event families:

- **Lifecycle:** `recorder_started`, `recorder_stopped`.
- **Operation declarations:** `operation_prescribed`, `operation_replaced`,
  `operation_reported`.
- **Execution observations:** `execution_started`, `execution_finished`.
- **Blocked protocol activity:** `protocol_violation`.
- **Known recording gaps:** `recorder_degraded`.

An execution start stores its execution ID, upstream tool name, argument HMAC,
optional upstream-declared tool annotations, and start time. A finish stores the
execution ID, tool, observed status, optional result HMAC, fingerprint status and
format, error code, optional error-message HMAC, duration, and finish time.

Observed terminal status is limited to `success`, `error`, `cancelled`, or
`unknown`. Agent reports use a separate status/outcome vocabulary and remain
claims even when an observed execution succeeded.

## Provenance

Every event uses exactly one of three provenance values:

1. `agent_declared` — objective, expected outcome, replacement, or terminal
   report supplied by the agent.
2. `proxy_observed` — an execution boundary and response classification visible
   to the proxy.
3. `recorder_generated` — lifecycle, degraded-window, or protocol-enforcement
   facts generated by Evidra.

Provenance identifies the source of a statement; it does not certify that the
statement is true outside that source's boundary. Derived reconciliation findings
are computed at read time and are not new stored provenance values.

## Hash chain and canonicalization

Before hashing, Evidra clears an event's `hash` and `signature` fields and encodes
the remaining envelope with JSON Canonicalization Scheme (JCS, RFC 8785). It then
computes SHA-256 over those canonical bytes and stores the lower-case hexadecimal
digest in `hash`.

Every event also stores the preceding event's hash in `previous_hash`. Sequence
and link checks can therefore detect modification, interior removal, insertion,
and reordering within the records a verifier receives. Without an external tail
anchor, truncation of the final records may not be detectable. The chain also
does not prove that an entire recorder directory was not replaced.

## Signatures

Each recorder creates or resumes a local Ed25519 private key in `signing.key`.
Every event signs the 32-byte SHA-256 event hash. `meta.json` stores the
corresponding public key, and verification checks every reported signature
against that key.

Because the private key, public-key metadata, and event file live in the same
directory, this is a local consistency boundary. A party able to replace the
whole directory can generate new keys and a new internally valid chain. The
ephemeral local key does not independently establish a person, organization,
machine, or trusted timestamp.

## Argument and result fingerprints

`digest.key` is a random 32-byte local HMAC key. Its non-secret
`digest_key_id` names the comparison domain; fingerprints made with different
keys are not compared or aggregated.

Arguments are JCS-canonicalized and stored as
`HMAC-SHA-256(digest_key, canonical_arguments)`. Equivalent JSON object key order
and whitespace therefore produce the same digest within one domain.

Results are not semantically normalized. Evidra fingerprints the exact upstream
JSON-RPC response frame with HMAC-SHA-256 when it is at most 4 MiB. Larger frames
record `omitted_oversize`; absent bytes record `unavailable`. Error message text
is represented by a separate HMAC when present.

Raw tool arguments and raw upstream response bodies are not stored in observed
event payloads. The proxy may store upstream-declared tool annotations verbatim,
and agent declaration/report text remains readable. HMAC does not protect a
low-entropy value from brute-force guessing by someone who can read the local key
or try a small candidate set.

## Coverage and degraded recording

The store marks itself unhealthy after an append or flush failure. If storage
later recovers, the next append first writes `recorder_degraded` with the known
window start, end, and reason.

Coverage is therefore a statement about degraded windows the recorder managed
to describe. `coverage=degraded` can coexist with a valid hash chain and valid
signatures. Conversely, `coverage=complete` means no persisted degraded event was
seen; it cannot prove that an abrupt or permanent failure left no unknown gap.

Every event is flushed from the buffered writer to the process-visible file.
The implementation does not call a host-storage synchronization primitive for
each event. Abrupt process, kernel, host, or storage failure may still lose or
damage the tail, so crash durability beyond the visible file is not promised.

## Verification

`evidra verify --dir <root>` reports per recorder:

- chain validity: sequence, predecessor links, and recomputed hashes;
- signature validity: signatures under that recorder's metadata public key;
- coverage: `complete` or `degraded` from recorded coverage evidence;
- record range, event counts, mode, upstream, and digest-key domain.

These are separate conclusions. Neither a valid signature nor complete reported
coverage upgrades agent declarations, upstream annotations, or reports into
independent truth.

Use an unfiltered verification run for whole-store decisions. A `--since` view
must not be read as establishing the integrity of records before its time
boundary. `evidra summarize` additionally surfaces unpaired execution starts and
other reconciliation facts; those are not cryptographic coverage conclusions.

## Threat model and limitations

The current format is useful when the recorder directory and keys remain under
the expected local owner, and a later accidental or partial edit should be
detectable. Its limits are explicit:

- replacement of the directory, metadata, and local keys is outside the signing
  boundary;
- the local public key has no external organizational identity or timestamp
  anchor;
- a copied digest key permits dictionary attacks and fingerprint comparison
  inside that key's domain;
- the recorder sees only calls routed through its endpoint;
- upstream tool annotations are unverified server declarations;
- clocks and actor IDs are locally supplied;
- buffered flush is not proof of persistence through abrupt host failure;
- a valid MCP response proves neither the upstream side effect nor the intended
  external-world outcome.

Evidra provides execution evidence and reconciliation at an MCP boundary. It is
not a sandbox, policy engine, remote attestation system, or external-state
verifier.
